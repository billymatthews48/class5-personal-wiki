# Building a Custom LLM: a tiny nanoGPT trained from scratch

**Class 4 · From Zero to AI Agents · Fall 26** · Author: Billy Matthews

I trained Andrej Karpathy's nanoGPT from scratch on a small word-level corpus, in two required
experiments:
- **A:** the supplied starter corpus.
- **B:** the starter corpus plus my own teaching material covering all eight eval extension skills.

Both experiments ran the fixed 48-case language eval before and after training. I then chatted
with the trained model through a terminal and a local web interface. The model has
2 transformer blocks, 4 attention heads, 64-number embeddings, a 48-token context and about
0.11–0.13 M parameters. It continues short sentences in the style of its corpus. It is not a
general assistant.

**The whole story in one line:** examples → predictions → loss → gradients → updates → changed
predictions. Every number below comes from the saved runs in [`llm_runs/`](llm_runs/).

[summarize_results.py](summarize_results.py).

**Main findings:**
1. The starter corpus could not attempt the 24 extension cases at all, because their words
   were missing. Doubling the training steps (A-6k) did not change that: 0/24 stayed 0/24.
   **More training cannot supply missing vocabulary.**
2. Adding focused teaching material raised coverage from 24/48 to 48/48, and raised the
   extension score from 0 to 19/24 (21/24 at 6,000 steps).
3. My first, over-strict corpus (B-v1) created blind spots that the relaxed v2 fixed. Longer
   training then mostly increased confidence, and unlocked copying names from the prompt.
4. **These 48 tests are a public development benchmark.** They guided my corpus choices, so
   these scores do **not** show generalization to unseen tests or broad language understanding.

## 3. How to run everything

All of this was tested on Windows 11 with Python 3.13 and CPU-only PyTorch 2.14. No GPU, API
key or pretrained weights are needed.

```sh
git clone <this repository> && cd <repository>
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt     # macOS/Linux: .venv/bin/python
```

**Windows note.** The notebook verifies SHA-256 hashes of its helper files. When I first cloned
the course repository, Git converted line endings to CRLF, and the notebook stopped with
"run_evals.py differs from this notebook's fixed version". This repository's `.gitattributes`
(`* -text`) prevents that conversion, so a fresh clone keeps the exact bytes. None of the helper
files were modified.

**Re-run an experiment.** Open a `custom_llm_*.ipynb` notebook with that environment and choose
*Run All*, or run `jupyter nbconvert --to notebook --execute <notebook> --inplace`. Each run
creates a new timestamped folder in `llm_runs/`.
- **Experiment A** needs `corpus/` to contain only `README.md`. In classroom mode the notebook
  adds every file in `corpus/`, so move `corpus/extension/` out first.
- **Experiment B** needs `corpus/extension/` in place. Regenerate it with
  `python make_teaching_corpus.py`, then audit it with `python check_extension_corpus.py`.

**Rerun the 48 evals on the saved final model** (no training, weights unchanged):
```sh
python run_evals.py --model llm_runs/20260923T003555_129361Z/model.pt --output results/my-final-evals
python run_evals.py --model llm_runs/20260923T003555_129361Z/model_untrained.pt --stage untrained --output results/my-untrained-evals
```
I did exactly this: see [results/rerun_evals/](results/rerun_evals/). The rerun matched the
notebook's result for all 48 cases, including every free continuation (45/48 final, 14/48 untrained).
Use a new `--output` folder each time.

**Chat with the final model:** see [section 10](#10-chat-interface).
```sh
python chat.py --model llm_runs/20260923T003555_129361Z/model.pt --transcript results/my-chat.json
python chat_web.py --model llm_runs/20260923T003555_129361Z/model.pt --transcript results/my-web-chat.json
```
Then open http://127.0.0.1:8765 for the web version. For other runs, replace the folder name
(see [llm_runs/README.md](llm_runs/README.md)). `model.pt` holds the full network and vocabulary.
`checkpoint.json` only holds embedding-viewer data. To inspect embeddings visually, open
[embedding-viewer.html](embedding-viewer.html) locally and load a run's `checkpoint.json`.

## 4. Corpus: sources, permissions and the extension material

**Starter corpus (both experiments).** These are the course's synthetic classroom sentences,
generated inside the notebook: business, finance, food, transport, software, health and education
templates. The manifest reports 6,200 base passages. After 1,608 duplicates are removed, **4,592 unique
passages** remain. Before the split and vocabulary, the notebook also withheld the 160 generated
sentences that contain a reserved eval prompt (see
[eval_separation.json](llm_runs/20260922T231357_098765Z/eval_separation.json)).

**Extension corpus (Experiment B).** I generated this myself with
[make_teaching_corpus.py](make_teaching_corpus.py) (fixed random seed, so it is reproducible).
It is plain UTF-8 text with no third-party material, so I can share it. It holds
**4,691 unique passages** across 8 files:

| File | Passages | What it teaches | Example passage |
|---|---|---|---|
| [grammar.txt](corpus/extension/grammar.txt) | 600 | singular/plural agreement (is/are, was/were), am, past/present/-ing verb forms | `the trees are big .yesterday he walked after lunch .` |
| [opposites.txt](corpus/extension/opposites.txt) | 500 | "the opposite of X is Y" with other pairs, plus contrasts for temperature, amount, sound | `the school was noisy , but the station was quiet .` |
| [negation.txt](corpus/extension/negation.txt) | 900 | "X is not A . it is B . X is B" corrections with colours, states and food | `the shirt was not red .it was blue .the shirt was blue .` |
| [references.txt](corpus/extension/references.txt) | 900 | who gave / received / called / thanked whom, across 18 names | `nora called nina .nina answered the call from nora .` |
| [sequence.txt](corpus/extension/sequence.txt) | 378 | first/then/last actions, earlier/later meals and vehicles | `first fill the jar .then carry it .the last action is carry .` |
| [spatial_relations.txt](corpus/extension/spatial_relations.txt) | 500 | inside/contains, above/below, left/right, north/south, including inverse relations | `the desk is above the shelf .the shelf is below the desk .` |
| [everyday_knowledge.txt](corpus/extension/everyday_knowledge.txt) | 313 | simple facts (ice, steam, umbrella, light) and "uses a X to Y" purposes | `an umbrella keeps you dry in the rain .` |
| [categories_and_analogies.txt](corpus/extension/categories_and_analogies.txt) | 600 | "a X is a Y" category pairs and "a young animal grows into an adult" | `a lamb grows into a sheep .a kitten grows into a cat .` |

**Why these categories?** The brief asks for at least two. I chose **all eight**, for two
reasons. First, Experiment A showed every extension case was unscorable for the same reason:
missing vocabulary (about 144 eval words, such as "opposite", "kitten", "umbrella", "below").
Second, my instructor emphasised how many evals the model can actually attempt. For each skill,
the material supplies the missing words *and* the pattern the skill needs. Negation needs "not A
… it is B → B". References need "the person who received … was <recipient>". Spatial relations
need inverse pairs like "X above Y → Y below X". Everything uses different people, objects and
wording from the eval items.

**Two technical details:**
- **Stories kept whole.** The notebook splits imported files at every ". " into separate
  passages, which would break 2–3 sentence stories apart. So the generator joins sentences
  inside a story with no space after the full stop (`red .it is`). The tokenizer produces
  exactly the same tokens (`red`, `.`, `it`), and the story stays one passage (at most 47 tokens).
- **Vocabulary budget.** The model keeps only the 509 most frequent training word types. I kept
  the combined vocabulary at 471 types, so no eval word would fall out as `<UNK>`.

**PDF extraction.** No PDFs were used, only UTF-8 `.txt` files. The runs' corpus manifests
([B](llm_runs/20260923T003152_798951Z/corpus_manifest.json),
[B-6k](llm_runs/20260923T003555_129361Z/corpus_manifest.json)) list all 8 files with their
SHA-256 hashes, previews, passage counts, **no warnings and no ignored files**. The files in
`corpus/extension/` match those hashes byte for byte.

**Split, vocabulary and unknown-token rates.** Duplicates are removed and then passages are split
90/10. Validation passages never produce weight updates. Parts of the same source file can appear
in both sets, and validation shares templates with training.

| | A (starter) | B (expanded) |
|---|---|---|
| Unique passages | 4,592 | 9,283 |
| Train / validation passages | 4,132 / 460 | 8,354 / 929 |
| Vocabulary (word types + `<UNK>`, `<BOS>`, `<EOS>`) | 133 + 3 = 136 | 471 + 3 = 474 |
| Training unknown-token rate | 0.0% | 0.0% |
| Held-out (validation) unknown-token rate | 0.0% | 0.036% |
| Reports | [manifest](llm_runs/20260922T231357_098765Z/corpus_manifest.json) · [vocabulary](llm_runs/20260922T231357_098765Z/vocabulary_report.json) · [split](llm_runs/20260922T231357_098765Z/split.json) | [manifest](llm_runs/20260923T003152_798951Z/corpus_manifest.json) · [vocabulary](llm_runs/20260923T003152_798951Z/vocabulary_report.json) · [split](llm_runs/20260923T003152_798951Z/split.json) |

The vocabulary is built **only from training passages**. B's held-out text contains a few words
that never appear in training, and those become `<UNK>`.

## 5. My three choices, predictions and what actually happened

| Choice | Value | Reason |
|---|---|---|
| **Corpus** | A: `CORPUS="classroom"` only. B: classroom plus `corpus/extension/` | A is the required baseline. B adds focused teaching material for all 8 extension skills (section 4). |
| **Training steps** | 3,000 (plus 6,000-step follow-ups) | The suggested starting budget, and it runs in about 1 minute on my CPU. A step is one batch of 32 passages and one weight update, not a full pass over the corpus. I added matched 6,000-step runs to test training length separately, changing one thing at a time. |
| **Learning rate** | 0.001 | The suggested default, kept identical so that runs are comparable. The notebook warms up over the first 100 steps and then follows a cosine decay down to 10% of the peak. |

**Why the learning rate matters.** An update is roughly *learning rate × the direction that
reduces the loss*.
- **Too large:** updates overshoot. The loss bounces around or diverges, and the embeddings are
  pushed into noise.
- **Too small:** each of the ~130,000 weights moves a tiny amount per step. After 3,000 steps the
  model is still close to random. You can see how small one early update is in
  [section 7](#7-how-the-model-learned-one-word-traced-end-to-end), where it changes a weight by 0.00001.

**Predictions (written in each notebook before training) against outcomes:**

| Run | What I predicted | What happened |
|---|---|---|
| A | Untrained: about random (1 in 4). Trained: good on starter patterns, okay on new wording, zero on extension. | ✅ 9/48 untrained (9/24 scorable, about chance). Trained 16/16, 4/8, 0/24 (unscorable). |
| B-v1 | More extension cases right than A's 0/24 | ✅ 15/24 |
| B (v2) | Higher than B-v1's 39/48 | ✅ 43/48 |
| B-6k | Slightly more accurate than 43/48, but only slightly | ✅ 45/48 (+2), with much higher confidence |
| A-6k | *(written by my AI assistant; I was away)* Extension stays unscorable; starter stays about the same | ✅ 0/24 extension; new wording 4 → 6 |

My written predictions were about the eval scores. I did not write separate predictions for the
loss or for a word's neighbours. The observed loss and neighbour changes are in sections 6 and 7.

**How to read these numbers:**
- **At step 0, the loss is almost exactly ln(vocabulary size):** ln 136 = 4.91 and ln 474 = 6.16.
  That is the loss of guessing uniformly at random, so the untrained model really is guessing.
- **The loss drops steeply, then flattens.** By step 1,500 it is below 1.0, and the second half
  of training adds little.
- **Validation stays close to training,** so there is no sign of heavy overfitting. In B the
  validation panel is even slightly lower, which is plausible noise from 20-passage panels.
- **Held-out passages share templates with training.** Low validation loss shows the model
  handles new combinations within familiar templates, not new kinds of text.
- **A and B losses are not directly comparable.** They have different corpora and vocabularies
  (predicting among 474 words is harder than among 136).
- **B-6k's loss barely moved between 3,000 and 6,000 steps** (0.84 → 0.81), yet its eval behaviour
  changed noticeably (section 8). A small loss change can hide a qualitative change.

## 7. How the model learned: one word traced end to end

These examples come from the final model (B-6k,
[tokenization.json](llm_runs/20260923T003555_129361Z/tokenization.json),
[inspection.json](llm_runs/20260923T003555_129361Z/inspection.json)). The same inspections
for A are in [its folder](llm_runs/20260922T231357_098765Z/inspection.json), and are summarised
at the end of this section.

**Corpus → tokens → IDs.** The corpus is just text. The tokenizer lowercases it and splits it
into words and punctuation. Each distinct token gets an arbitrary integer ID, which is a label,
not a meaning. One real training passage:

| `<BOS>` | maya | lent | an | apple | to | nina | . | nina | thanked | maya | . | `<EOS>` |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 253 | 237 | 12 | 16 | 410 | 268 | 4 | 268 | 404 | 253 | 4 | 2 |

Training turns this into **inputs** (every ID except the last) and **targets** (every ID
shifted one to the left). At each position the model must predict the next ID. After
"… nina thanked" the target is 253 (maya).

**ID → vector (embedding).** Each ID selects one row of a 474 × 64 table of learnable numbers:
its **embedding**. The word **"customer" has ID 109**. The first 8 of its 64 numbers:

| | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | length of all 64 |
|---|---|---|---|---|---|---|---|---|---|
| Before training (random) | −0.0149 | 0.0560 | 0.0026 | −0.0270 | 0.0127 | −0.0429 | 0.0151 | 0.0245 | 0.16 |
| After 6,000 steps | 0.0526 | −0.0085 | 0.1368 | −0.0486 | −0.1172 | 0.0061 | 0.0734 | 0.1179 | 0.57 |

No single coordinate means anything on its own. What matters is how whole vectors relate. By
cosine similarity across all 64 numbers, customer's nearest neighbours changed:

| Word | Nearest neighbours before training | Nearest neighbours after training |
|---|---|---|
| customer | fill, the, loud | **consumer 0.97, shopper 0.97, subscriber 0.96** |
| salmon | arrived, credit, cup | **trout 0.90, shark 0.85, tuna 0.85** |
| cold | you, walk, made | **hot 0.74**, hard 0.59, noisy 0.59 |
| blue | person, `<BOS>`, dry | **white 0.70, brown 0.69, red 0.61** |

Nobody told the model what these words mean. Words that appear **in the same positions,
surrounded by the same words**, need the same predictions, so gradient descent gives them
similar vectors. That is also why **"cold" ends up next to its opposite "hot"**: they fill the
same slots ("the soup was ___"). Similar vectors mean *interchangeable in context*, not *same
meaning*. The course's 3D embedding viewer compresses 64 numbers into 3 with PCA, which loses
information. So 3D closeness can mislead, while these neighbour lists use all 64 numbers.

**The neural network.** The embedding (plus a position embedding) passes through 2 transformer
blocks. Each block has causal self-attention (4 heads), then a small feed-forward network of
weighted sums and a GELU non-linearity, with residual connections and LayerNorm. A final layer
scores all 474 vocabulary entries. These scores (logits) become probabilities through softmax.
All ~133,000 numbers involved are **weights**, and training adjusts all of them.

**Loss, gradient and one real update.** For each position the loss is −log(probability the
model gave the correct next token). A correct guess with probability 1 costs 0. A guess with
probability 1/474 costs 6.16. PyTorch's backpropagation computes the **gradient** of the average
loss with respect to every weight: which direction, and how strongly, each weight should move to
reduce the loss. AdamW then updates the weights. The notebook saved the very first update to
coordinate 0 of "customer":

| Value before | Gradient | Learning rate at step 1 | Value after | Change |
|---|---|---|---|---|
| −0.0148768 | −0.00155 | 0.00001 (warmup: 0.001 × 1/100) | −0.0148668 | +0.0000100 |

The gradient is **negative**. So *increasing* this number would lower the loss, and the update
moved it **up**. AdamW normalises each step, so the first step's size is about the learning rate
itself (0.00001). On its own that change is microscopic. Repeated for all 133,504 weights over
6,000 steps, it turned random vectors into the structured ones above.

**Predictions: next-token probabilities.** Given the prefix **"the customer"**:

| | Top next-token probabilities |
|---|---|
| Before training | customer 0.45%, bird 0.35%, stayed 0.32%, explains 0.30%, tool 0.30% (nearly uniform, 1/474 = 0.21%) |
| After training | **reviewed 18.4%, recommended 18.1%, selected 16.4%, returned 16.0%, ordered 15.3%**, compared 11.7% |

The trained model has learned that a customer is followed by a shopping verb.

**Attention uses earlier context.** For each position, each attention head computes how much
to "look at" every **earlier** token. It is causal, so it never looks at later ones. The weighted
mix of those tokens' vectors then informs the prediction. The notebook's first-layer, first-head
attention for `<BOS> the customer`:

| Row (current position) | → `<BOS>` | → the | → customer |
|---|---|---|---|
| `<BOS>` | 1.00 | – | – |
| the | 0.31 | 0.69 | – |
| customer | 0.12 | 0.20 | **0.69** |

This is what lets the final model answer "the hat is not pink . it is white . the hat is" → **white**
(section 10). The answer word is not the last word. It has to be found by looking back through
the context. The 48-token context window limits how far back it can look.

**From probabilities to generated words; temperature.** To generate, the model divides the
logits by the **temperature**, converts them to probabilities, samples one token, appends it, and
repeats until `<EOS>` or 24 tokens. Temperature changes only this sampling step. **No weights change.**
[temperature_comparison.json](llm_runs/20260923T003555_129361Z/temperature_comparison.json) uses
the same start and the same sampling seed for all three:

| Temperature | Third sample (same start, same seed) |
|---|---|
| 0.3 | "the local truck was mentioned in the journey report yesterday ." (all four samples use the same safe template) |
| 0.8 | "emma did not buy pear . she bought tea . emma bought tea ." |
| 1.2 | "emma did not **cups** tea . she **played in the morning yesterday** ." (unlikely words sneak in and the grammar breaks) |

Low temperature sharpens the distribution toward the most likely words. High temperature
flattens it, so it gets more varied and more errors. In Experiment A, 0.8 and 1.2 produced
identical samples. The model trained on the narrow starter corpus was so confident that even a
flattened distribution picked the same words.

**The same trace in Experiment A** ([inspection.json](llm_runs/20260922T231357_098765Z/inspection.json)):
- "customer" had ID 28.
- Its neighbours went from bus / educator / helped to **shopper / client / buyer (0.98)**.
- Its first update was −0.0575919 → −0.0576019. The gradient was +0.00069 (positive), so the
  weight moved *down*.
- After "the customer" the top predictions became reviewed 17.8%, recommended 17.1%, ordered 16.8%.

## 8. The 48 language evals

**Scoring rules** (unchanged course runner, [run_evals.py](run_evals.py), suite
[evals/language_evals.json](evals/language_evals.json)):
1. **Only the prompt is fed to the model.** It never sees the four choices or the answer key.
   Weights are never updated.
2. **The case scores 1** if the correct word has the highest probability among the four choices.
   A wrong answer or a tie scores 0. Random choice averages 25%.
3. **Unscorable cases score 0.** If any prompt or choice word is outside the model's vocabulary,
   or the prompt is too long, the case is unscorable. It counts as 0 in the **all-case success
   rate**, and is excluded from **scorable accuracy**. **Coverage** is the share of scorable cases.
4. **A free continuation is saved separately and not scored.** It is sampled at temperature 0.8
   with a fixed per-case seed, up to 24 tokens.

The four required result sets are linked in [section 1](#1-results-at-a-glance). Every case for
every run is in [results/eval_comparison.md](results/eval_comparison.md).

| Starter: domain place (8) | 8/8 | 8/8 | 8/8 |

**Is the gain from vocabulary coverage, learned patterns, or both? Both, and the runs let me
separate them:**
- **Coverage alone** explains why A scores 0/24 on the extension group: those cases were never
  attempted. A-6k shows more steps cannot fix this (still 0/24). Coverage is necessary but not
  sufficient. B's **untrained** model has full coverage too, but scores only 8/24 on the extension
  group (about chance).
- **Learned patterns** explain the jump from 8/24 untrained to 19/24 trained. Some correct answers
  are **not** the most frequent word in that slot, and must be found in the prompt. Examples from B-6k:
  - "the box is not red . it is blue . the box is" → **blue 97%** (red 0.2%)
  - "omar called nina . nina answered the call from" → **omar 98%**
- **New wording improved from 4/8 (A) to 8/8 (B)**, even though those cases use starter
  vocabulary. The more varied B corpus seems to have helped the model handle unfamiliar
  sentence structures. A-6k reached only 6/8.

**Free continuations and multiple choice can disagree.** Examples from the final runs (all in
[eval_comparison.md](results/eval_comparison.md)):

| Prompt | Multiple-choice pick (B-6k) | Free continuation (B-6k) |
|---|---|---|
| the opposite of hot is | cold ✓ | "cold ." |
| the lamp is above the desk . the desk is | below ✓ | "below the lamp ." |
| water freezes into | ice ✓ | "ice when it is cold ." |
| a person uses an umbrella to stay | dry ✓ | "warm ." (it picks dry among the four choices, but freely writes something else) |
| the opposite of noisy is | quiet ✓ | "small ." |
| maya lent a book to leo . leo thanked | leo ✗ | "leo ." |

**Failures of the final model (3/48), and why:**
1. **"maya lent a book to leo . leo thanked" → leo (85%), wanted maya.** The model now copies names
   confidently, but it copies the most recent name instead of the giver. At 3,000 steps it
   spread its probability thinly across the names (2–7% each, picking nora). Longer training learned *copying*, but not
   reliably *which role* to copy.
2. **"the dogs" → was (51%) vs are (19%).** The eval prefix "the dogs" can never appear in
   training (it is reserved), so agreement had to transfer from "the cats are", "two dogs are"
   and similar. At 3,000 steps it was right, but only by 23% to 22%. At 6,000 it tipped the other way.
3. **"to see in a dark room we turn on a" → pillow (3.7%) vs light (0.7%).** Every choice has low
   probability. The prompt's *shape* matches my training sentence "to sleep well we use a soft
   pillow", and the model follows shape over meaning.

**How the extension material changed things, v1 → v2.** My first corpus (B-v1, 39/48) kept every
eval word out of the matching sentence shapes. That created blind spots. For example, the door
was only ever taught as "not closed → open", so the model answered "open". Allowing plain facts
and shared shapes (v2) fixed the salmon/fish, kitten/cat and box-colour cases (section 9).

**This is a development benchmark.** I looked at these 48 public tests while designing and
revising the corpus. A claim about unseen generalization would need new tests that never guided
my choices.

## 9. Keeping the evals out of training

**Rules.**
- **Never allowed in training text or vocabulary building:** eval prompts, the answer key,
  answer lists, eval outputs, or chat transcripts.
- **Allowed** (the brief's words): *ordinary words and underlying subject knowledge*.

**Checks.**
1. **The notebook's own checks** (both experiments).
   - It withheld 160 classroom sentences containing reserved test prefixes before the split and
     the vocabulary.
   - It rejects imported files containing any exact eval prompt, and any corpus folder that
     includes `evals/`.
   - See [A's eval_separation.json](llm_runs/20260922T231357_098765Z/eval_separation.json) and
     [B's](llm_runs/20260923T003152_798951Z/eval_separation.json). Both runs completed without
     a leakage error.
2. **My independent pre-training audit**, [check_extension_corpus.py](check_extension_corpus.py),
   saved to [results/extension_corpus_audit.json](results/extension_corpus_audit.json). The final
   v2 corpus has:
   - **0 exact eval prompts**
   - **0 near-copies**: no passage contains *all* of an eval item's distinctive words plus its
     answer (for example box + red + blue, or ava + tea + milk), in either order
   - 48/48 cases with full vocabulary
3. **Separation of paths.**
   - The generator never reads `evals/`.
   - `CORPUS_FOLDER` is `corpus/` only.
   - Eval results, reruns and chat transcripts live in `llm_runs/` and `results/`, never in `corpus/`.

**What still overlaps ("bleeding"), disclosed on purpose.**
- **v1 ("strict") went beyond the rules.** It also kept each eval's specific words out of the
  matching sentence shapes. The audit caught and fixed near-copies during development, for example
  "the taxi arrived before the bus . the vehicle that arrived later was the bus".
- **Why v2 is different.** My instructor said he checks for intentional cheating but expects some
  bleeding. So for v2 I redrew the line at the brief's wording.
- **Plain facts are stated in v2**, for example "a salmon is a fish" (27 passages), "a kitten grows
  into a cat" (14) and "an apple is a fruit" (25).
- **Eval sentence shapes are reused with other people and objects**, for example "nora called nina .
  nina answered the call from nora".
- **Some passages differ from an eval item's key words by exactly one word.** The audit counts these:
  - "the call from" omar/nina frame: 47
  - two of box/red/blue: 33, and two of door/open/closed: 36 (these include unrelated
    sentences such as "a child uses a key to open a door")
  - pencil: 7, cup/wash/dry: 7, apple/carrot: 6, robin/salmon: 5, ava/tea/milk: 2
- **Consequence:** some B scores reflect directly taught facts and familiar frames rather than
  reasoning. I report them as a development benchmark.

## 11. What stayed fixed, what changed in training, what changed only at inference

- **Fixed across all runs:**
  - the notebook code and nanoGPT architecture (2 blocks, 4 heads, 64-dimensional embeddings,
    48-token context, batch 32)
  - the training seed (42), learning rate (0.001) and schedule shape
  - the 90/10 passage-split method and the 20 + 20 loss panels
  - the classroom sentence generator
  - the unchanged 48-case suite (sha256 `1d7c503f…`) and scoring runner
  - the generation settings for samples and evals (temperature 0.8, seed 2026 for evals, 24 tokens)
- **Changed between experiments (training):**
  - the corpus (starter only → starter plus extension files, v1 then v2)
  - therefore the vocabulary (136 → 474) and parameter count
  - the training steps (3,000 vs 6,000), one change at a time
- **Changed only at inference (no weight updates):**
  - the temperature (0.3 / 0.8 / 1.2 comparison)
  - chat prompts and seeds
  - eval prompts

  The eval runner and chat interfaces load the saved weights and never update them.

## 12. Limitations and next experiment

**Limitations observed:**
- **It pattern-matches on sentence shape, not meaning.** "to see in a dark room we turn on a" →
  "pillow", because the prompt looks like "to sleep well we use a soft pillow".
- **Role tracking is fragile.** It confidently copies the wrong name in
  "maya lent a book to leo . leo thanked" → leo.
- **It cannot handle questions or new words.** "what is the capital of france ?" produced only ".".
- **It is narrow.** The synthetic corpus has repeated templates, and validation shares those
  templates, so the low validation loss does not show broad knowledge.
- **The scores are not a generalization result.** The corpus was tuned while looking at these
  48 public tests, and some facts are taught directly (section 9).

**Proposed next experiment: a held-out generalization test.**
1. Write about 24 **new** eval cases for the same eight skills, with new names, objects and
   sentence frames, **before** looking at any model output.
2. Score B-6k on them *without* changing the corpus.
3. Compare with its 21/24 development score. The gap between the two measures how much of the
   improvement is real skill rather than tuning to the public tests.

A second, targeted test: add training stories where the *giver* is the answer after a verb
("X lent … to Y . Y thanked X", with varied verbs). Then check whether the "most recent name"
error disappears, without that eval's frame ever appearing.
